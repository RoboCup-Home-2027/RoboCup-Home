# 实物小车接收与联调完整工作清单

> 适用项目：RoboCup@Home 家庭组 ROS2 Humble 机器人
>
> 目标：从“刚拿到实物”推进到“可重复完成比赛任务”，同时保留原始系统、可回退配置和完整测试证据。
>
> 核心原则：先记录与备份，再通电；先单模块，再集成；先架空低速，再落地；仿真通过不等于真机通过。

## 0. 当前已知状态

仓库当前目标平台为 RDK X5、STM32 F407/C30D、WHEELTEC 麦克纳姆底盘、镭神 N10P、Gemini 深度相机和 ROS2 Humble，使用 `ROS_DOMAIN_ID=31`。

当前已经完成：

- ROS2 工作区和统一比赛入口；
- 68 个功能包的虚拟机构建；
- Gazebo、SLAM Toolbox、地图保存和仿真运动链路；
- 仿真地图及 rosbag 记录。

当前尚未在实物上确认：

- 主控、C30D、雷达、相机和机械臂的准确型号；
- 真实麦克纳姆四轮方向、编码器和里程计；
- N10P、Gemini、IMU、TF；
- ArUco、TTS、Nav2和统一比赛入口；
- 电脑断开后小车能否独立运行。

因此，禁止把仓库中的“目标硬件”直接当作实物事实。

## 1. 人员、设备与职责

### 1.1 最少人员

实车运动测试至少两人：

- 操作员：运行命令、观察终端；
- 安全员：守在电机使能/急停旁，观察线缆、车轮和机械臂。

机械臂或自动导航测试建议三人，第三人负责场地清空和记录。

### 1.2 建议携带

- 小车原装电池、充电器和钥匙/电源配件；
- MacBook、充电器、USB-C 供电设备；
- Windows 调试电脑及充电器，用于 Ubuntu 虚拟机、RViz2；
- 插线板、网线、USB 数据线、显示器/HDMI线、键盘鼠标；
- 稳固的小车架空支架；
- 螺丝刀、扎带、绝缘胶带、标签纸；
- 万用表，仅由熟悉电气安全的成员使用；
- U盘或移动硬盘，用于离线备份；
- 手机热点作为外网备用，但不得在未知情况下改掉小车网络。

### 1.3 计算设备分工

| 设备 | 职责 |
|---|---|
| RDK X5 | 运行底盘、雷达、相机、SLAM/Nav2、视觉、TTS和比赛程序 |
| STM32/C30D | 电机、编码器、IMU、舵机等底层控制 |
| MacBook | Codex、Git、SSH、日志、文件同步和现场监控 |
| Windows + Ubuntu虚拟机 | RViz2、TF/地图图形化调试、必要的多机 ROS2 工具 |

比赛运行不得依赖笔记本持续在线。笔记本只用于部署、监控和救场。

### 停止条件

发现以下任一情况，不得通电：

- 裸露导线、松脱电源线、烧焦痕迹或异味；
- 电池鼓包、破损、漏液或规格不匹配；
- 机械结构松动、车轮或机械臂可能脱落；
- 电源极性、接口用途或充电器不明确。

## 3. 机械与电气静态检查

- [ ] 螺丝和支架牢固，雷达水平且无遮挡；
- [ ] 相机固定，不与机械臂运动范围冲突；
- [ ] 麦克纳姆轮安装方向与滚子方向一致；
- [ ] 四轮离地手动转动时无明显卡滞；
- [ ] 线缆不会卷入车轮、夹爪或旋转关节；
- [ ] 电池固定，插头牢固；
- [ ] 电机使能开关可识别，初始置于关闭状态；
- [ ] 已明确断电方式和安全员位置；
- [ ] 机械臂周围至少留出完整运动空间。

不要根据感觉调整舵机零位，不要手掰带电舵机。

## 4. 第一次通电与C30D自检

### 4.1 第一次通电

1. 小车可靠架空或对车轮止动，电机使能关闭；
2. 机械臂运动范围清空；
3. 通电后记录 OLED、蜂鸣器、主控和传感器指示灯；
4. 根据 C30D 厂商资料，上电后前 10 秒保持车体静止，等待 IMU 零点计算；
5. 出现异味、异常发热、连续报警或舵机剧烈抖动时立即断电。

### 4.2 C30D辅助质检

仅在确认固件支持该功能后进行。资料指出 2024-11-01 之后的相应固件支持质检模式。

1. 上电静置超过 10 秒；
2. 按住用户按键，再按复位按键；
3. 单击用户按键进入下一项，双击退出；
4. 测试电机前必须把四轮完全架空；
5. 电位器测试前记录原车型，退出前恢复原车型。

记录结果：

| 模块 | 结果 | 备注 |
|---|---|---|
| 电位器/车型 | 未测 | |
| 四路电机 | 未测 | 转向、编码器 |
| IMU | 未测 | 静止和晃动数据 |
| 舵机/机械臂 | 未测 | 各关节动作 |
| 蜂鸣器 | 未测 | |
| 电机使能开关 | 未测 | |
| 蓝牙 | 未测 | 可后置 |
| ROS串口 | 未测 | 设备、波特率 |

此阶段不烧写 STM32。只有在确认 C30D版本、编码器类型、减速比、底盘车型和机械臂自由度全部匹配后，才允许讨论固件更新。

### 5.3 多机ROS2网络验收

需要在Ubuntu虚拟机运行RViz2时，不能只检查 `ROS_DOMAIN_ID`：

- 虚拟机网卡使用桥接模式并与RDK X5处于同一网段；
- 两端均设置 `ROS_DOMAIN_ID=31`；
- 两端检查 `ROS_LOCALHOST_ONLY=0`或未设置；
- 两端记录 `RMW_IMPLEMENTATION`，避免使用不兼容的RMW配置；
- 检查防火墙、组播和多网卡路由；
- 使用ROS2官方talker/listener做无运动验证，确认双方能互见同一节点和话题。

```bash
echo "$ROS_DOMAIN_ID"
echo "$ROS_LOCALHOST_ONLY"
echo "$RMW_IMPLEMENTATION"
ip -brief address
ros2 node list
ros2 topic list
```

ROS1机械臂节点不能直接加入ROS2通信域；必须先确定Bridge或原生ROS2适配方案。

## 8. 仓库与车载工作区对比

仓库代表团队开发基线，车载工作区代表实物当前可运行状态；两者都不能未经比较就覆盖另一方。

由Codex完成：

1. 列出两边功能包和版本；
2. 对比 `turn_on_wheeltec_robot`、雷达、相机、Nav2和消息包；
3. 找出车载特有配置、设备规则和已调参数；
4. 标记仓库特有的比赛包、仿真包和统一入口；
5. 形成差异报告；
6. 明确哪些文件以车载为准、哪些以仓库为准；
7. 经人工确认后再制定逐文件合并方案。

不要首先在 RDK X5 上执行全量 `colcon build`。先验证原有安装空间能否运行，再决定是否增量编译。

### 8.1 仓库代码受控部署到RDK X5

只有完成差异报告并得到人工确认后才部署。禁止覆盖 `~/wheeltec_ros2`。

1. 记录准备部署的Git提交号：

   ```bash
   git rev-parse HEAD
   ```

2. 在RDK X5上建立独立版本目录，例如 `~/robocup_releases/<提交号>/`；原厂工作区保持不动。
3. 将固定提交克隆/同步到该目录，检查差异和文件清单。
4. 在新目录中加载系统ROS，不加载旧工作区overlay：

   ```bash
   source /opt/ros/humble/setup.bash
   colcon list
   colcon build --symlink-install --packages-up-to robocup_competition_bringup
   ```

5. 构建失败时记录缺失依赖，不修改系统Python/ROS版本，不用ROS1包替代ROS2依赖。
6. 架空车轮，在新shell中加载新版本的 `install/setup.bash`，先做无运动的包、节点和参数检查。
7. 只有通过分模块验证后，才把新版本标记为比赛候选。

回退方式：打开全新shell，只加载原厂 `/opt/ros/humble` 和 `~/wheeltec_ros2/install/setup.bash`，不加载候选release；确认旧版本节点恢复。每次部署必须在 `docs/TEST_RECORD.md` 记录提交号、构建命令、结果、激活路径和回退结果。

禁止整目录反向rsync、禁止 `--delete`、禁止直接在原厂工作区上执行批量覆盖。

## 9. 单模块真机验证

严格按以下顺序。每完成一个模块，记录命令、时间、输出、结论和失败现象。

除非另有说明，本节至第15节的命令均在RDK X5、ROS2 Humble、真机工作区中执行。每次启动前先确认实际overlay和参数：

```bash
ros2 pkg prefix <包名>
ros2 pkg prefix --share <包名>
find "$(ros2 pkg prefix --share <包名>)/launch" -maxdepth 1 -type f 2>/dev/null
ros2 launch <包名> <启动文件> --show-args
```

确认 `use_sim_time:=false`、车型、串口、地图和参数文件均指向真机后，才运行正式启动命令。本文中的launch均为候选入口，不等同于已经真机验证。

### 9.1 底盘驱动、编码器和里程计

首次软件运动测试必须架空四轮，安全员守在使能开关旁。

确认包存在后启动候选底盘入口：

```bash
export ROS_DOMAIN_ID=31
source /opt/ros/humble/setup.bash
source ~/wheeltec_ros2/install/setup.bash
ros2 launch turn_on_wheeltec_robot turn_on_wheeltec_robot.launch.py
```

在另一个终端只读观察：

```bash
ros2 node list
ros2 topic list
ros2 topic echo --once /odom
ros2 topic info /cmd_vel -v
```

经过人工确认后才启动键盘控制。只做短按、低速、单方向测试，并确保松键停车：

```bash
ros2 run wheeltec_robot_keyboard wheeltec_keyboard
```

验收：

- [ ] 四轮前后方向正确；
- [ ] 左右侧移和旋转符合麦克纳姆运动；
- [ ] 四路编码器都有反馈，方向符号合理；
- [ ] `/odom` 连续更新；
- [ ] 松键/停止后速度归零；
- [ ] 无持续串口错误、异常发热或机械摩擦。

任何一轮方向错误时停止，不通过“交换多根线”盲试；先检查车型参数、轮序、编码器和固件匹配关系。

### 9.2 IMU

```bash
ros2 topic list | grep -i imu
ros2 topic echo --once /imu/data
ros2 topic hz /imu/data
```

验收：静止时数据稳定，缓慢转动车体时对应轴变化，坐标方向与机器人模型一致。

### 9.3 N10P激光雷达

```bash
ros2 launch turn_on_wheeltec_robot wheeltec_lidar.launch.py
ros2 topic hz /scan
ros2 topic echo --once /scan
```

验收：

- [ ] `/scan` 频率稳定；
- [ ] 距离值合理，无持续全零/无穷；
- [ ] 雷达正前方与 `base_link` 正前方一致；
- [ ] 移动物体时扫描明显变化；
- [ ] 无USB反复掉线。

### 9.4 Gemini相机

先用 `lsusb` 和包列表确认驱动，再启动实际相机入口。厂商候选命令为：

```bash
ros2 launch turn_on_wheeltec_robot wheeltec_camera.launch.py
```

检查实际话题：

```bash
ros2 topic list | grep -E 'image|camera|depth'
ros2 topic hz <实际图像话题>
ros2 topic echo --once <实际camera_info话题>
```

验收：RGB图像正常、深度有效、时间戳连续、`camera_info`存在、图像方向正确。

### 9.5 TF与机器人模型

在底盘、雷达、相机都启动后检查：

```bash
ros2 run tf2_tools view_frames
ros2 run tf2_ros tf2_echo base_link laser_link
```

实际 frame 名称以话题和 URDF 为准。

验收：至少能形成 `odom → base_link → laser/camera` 连续链路，无重复父节点、跳变或明显错误安装角。

### 9.6 机械臂

机械臂最后测试。当前厂商机械臂资料主要是 ROS1 Melodic，不代表实车环境。

开始前必须确认：

- [ ] 4/6自由度；
- [ ] 初始姿态和舵机接口；
- [ ] 当前控制栈是 ROS1、ROS2还是串口程序；
- [ ] 运动范围完全清空；
- [ ] 有独立停止方式。

先做硬件自检或单关节小步进，不直接运行抓取、正逆解或自动轨迹。

## 10. 建立第一份真机数据基线

各模块通过后，记录不含原始相机大流量的话题：

```bash
mkdir -p ~/robocup_bags
cd ~/robocup_bags
ros2 bag record /scan /odom /tf /tf_static /imu/data /cmd_vel
```

只在需要时单独录制压缩图像，避免磁盘快速写满。记录完成后运行：

```bash
ros2 bag info <bag目录>
```

真机基线至少包含：

- 静止30秒；
- 低速直行、后退、左右侧移、原地旋转；
- 雷达周围有人移动；
- IMU缓慢转向；
- 所有测试结束后的零速度。

bag大文件不提交Git；把文件名、时间、硬件配置和摘要写入 `docs/TEST_RECORD.md`。

## 11. 小范围SLAM验证

前置条件：底盘、编码器、`/odom`、`/scan`和TF全部通过。

```bash
ros2 launch wheeltec_slam_toolbox online_sync.launch.py
```

使用Windows Ubuntu虚拟机中的RViz2观察。若采用多机ROS2，两端都设置：

```bash
export ROS_DOMAIN_ID=31
```

先在约3 m × 3 m无人的区域低速建图：

- 先原地慢转检查地图是否跟随；
- 再走小矩形并回到起点；
- 检查闭环、墙体重影和定位跳变；
- 不立即在完整场地高速建图。

验收：

- [ ] 地图方向稳定；
- [ ] 静态墙体不过度重影；
- [ ] 回到起点后闭环误差可接受；
- [ ] TF和节点无持续报错；
- [ ] 急停/停止始终有效。

保存地图后，把 `.pgm/.yaml`、场地版本、日期和对应参数一起版本化。仿真地图不得冒充真机比赛地图。

## 12. Nav2分级验证

前置条件：真机地图已保存，AMCL/TF稳定，底盘停止机制通过。

```bash
ros2 launch wheeltec_nav2 wheeltec_nav2.launch.py
```

测试顺序：

1. 不发目标，仅观察定位；
2. 发送距离小于1 m的单点目标；
3. 单点直线；
4. 单点转弯；
5. 狭窄门洞；
6. 多点巡航；
7. 静态障碍；
8. 人员缓慢经过的动态障碍；
9. 目标不可达和定位异常恢复；
10. 入口—房间—出口完整路线。

每级连续成功3次才进入下一级。

重点参数：footprint、膨胀半径、最大线/角速度、加速度、到点容差、局部规划器、恢复行为。每次只改一组相关参数并记录前后结果。

验收目标：

- 连续3次完成指定路线；
- 关键点误差约0.3 m以内；
- 不碰撞家具或门框；
- 障碍出现时减速/停车/重规划；
- 取消目标、节点异常或通信中断时能清零速度。

## 13. 视觉与寻物

先稳定基线，再增加模型复杂度：

1. 相机固定和内参确认；
2. ArUco/数字标签单帧识别；
3. 连续3帧一致确认；
4. 相机坐标到 `base_link/map` 的 TF；
5. 房间区域归属；
6. YOLO真实物体识别；
7. RGB-D距离和三维位置；
8. 导航—识别—确认—播报闭环。

测试光照、遮挡、偏角、距离和运动模糊。记录类别、置信度、坐标、时间戳和失败原因。

ArUco用于比赛稳定基线，YOLO作为增强能力；不要让YOLO部署阻塞导航基线。

## 14. TTS与交互

确认RDK X5架构与TTS动态库匹配，密钥/APPID不得提交到仓库。

依次验证：

- [ ] 单句离线播报；
- [ ] 目标名称；
- [ ] 房间名称；
- [ ] 任务完成；
- [ ] 定位、识别、网络和硬件异常；
- [ ] 语音失败时屏幕/日志/动作回退。

语音节点不得阻塞导航和安全停车。

## 15. 统一比赛入口集成

ros2 launch robocup_competition_bringup competition_bringup.launch.py

集成顺序：

6. YOLO/RGB-D；

## 16. 安全与故障注入

必须主动验证：

- [ ] 键盘/任务停止后 `/cmd_vel` 归零；
- [ ] 激光断开或 `/scan` 超时；
- [ ] 相机断开；
- [ ] 定位大幅跳变；
- [ ] 目标标签丢失；
- [ ] Nav2目标不可达；
- [ ] SSH/笔记本断开；
- [ ] 外网不可用；
- [ ] 某节点退出；
- [ ] 电量不足。

不得用真实碰撞、运动中热插拔或电池深度放电验证安全策略。传感器故障优先通过停止节点、暂停话题或受控超时注入；物理插拔只能在车体静止、电机禁用且按设备要求断电后进行。

| 故障场景 | 期望行为 |
|---|---|
| teleop/遥控控制链断开 | 速度在设定超时内归零并停车 |
| 仅监控用SSH/MacBook断开 | RDK X5上的自主任务继续，日志不中断 |
| ROS控制链或关键节点退出 | 停车并报告故障 |
| `/scan`、里程计、定位或TF失效 | 在设定超时内停车，禁止盲走 |
| 相机/识别失效 | 导航是否继续由任务状态机明确决定，不得误报识别成功 |
| 外网断开 | 离线比赛主流程继续；联网增强功能降级 |
| 低电量 | 通过阈值注入或受控换电演练验证，禁止深度放电 |

每一项都要在参数表中填写超时值、触发方式、实际行为和日志证据。

### 16.1 紧急停止卡

运动测试前打印或抄写并放在操作台：

1. 安全员始终能触及电机使能开关/物理急停；
2. 失控时优先关闭电机使能；若仍有机械臂或其他危险动作，立即断主电；
3. 操作员对当前前台launch按 `Ctrl+C`，取消Nav2目标或teleop输入；
4. 不把“发布一次零速度”当作唯一急停，因为其他发布者可能继续覆盖；
5. 确认车轮物理停止，再检查 `/cmd_vel` 发布者和消息；
6. 未查明原因前不得重新使能。

当天开始测试前必须填写：物理使能/急停位置、操作人、安全员、断电方式、软件停止入口。

### 16.2 数字化验收矩阵

“稳定、合理、明显、可接受”必须转化为数字。首次实测后由团队冻结目标值：

| 指标 | 目标值 | 实测值 | 证据 |
|---|---:|---:|---|
| `/scan`平均频率/最低频率 | 待定 | | 日志/bag |
| IMU平均频率/最大丢帧 | 待定 | | 日志/bag |
| TF最大延迟 | 待定 | | tf工具 |
| 静止里程计漂移（60秒） | 待定 | | bag |
| 直行规定距离误差 | 待定 | | 尺量/bag |
| 原地旋转规定角度误差 | 待定 | | 尺量/bag |
| SLAM回环位置/角度误差 | 待定 | | 地图/记录 |
| Nav2固定路线超时 | 待定 | | 任务日志 |
| 关键点到达误差 | 约0.3 m以内，实测后冻结 | | 尺量/定位 |
| 完整任务人工干预次数 | 0 | | 视频/日志 |
| 碰撞次数 | 0 | | 视频/记录 |

固定路线、目标点、目标物集合、时间上限和成功条件必须对应正式比赛规则，并写入测试记录；否则“连续3次成功”不具可比性。

## 17. 比赛部署

比赛版本必须固定：

- Git提交号；
- 地图文件及校验值；
- Nav2、相机、雷达、视觉参数；
- 主控系统和ROS版本；
- 启动命令；
- 回退命令；
- 已知问题；
- 对应测试记录。

推荐最终只有一个比赛启动入口，但在确认稳定前不要急于配置开机自启动。配置后必须验证：

- 重启后启动顺序正确；
- 不会同时启动重复驱动；
- 电机不会在无人确认时自动运动；
- 可通过明确命令停止全部比赛节点；
- MacBook断开后任务仍运行。

## 18. 完整比赛验收

至少进行：

- 3次冷启动完整任务；
- 3次热重启完整任务；
- 3次入口—多房间—寻物—播报—出口；
- 1次无外网；
- 1次笔记本中途断开；
- 1次目标不可达；
- 1次标签未找到；
- 1次动态障碍；
- 1次低电量或更换电池流程演练。

每次记录：开始/结束时间、成功与否、失败阶段、地图/代码版本、电量、日志和修复措施。

只有连续3次无人工干预完成完整流程，才标记“可比赛”。

## 19. 每次调试结束的收尾

- [ ] 停止所有运动节点并确认速度归零；
- [ ] 电机使能关闭，小车断电；
- [ ] 检查电机、驱动板、电池和主控温度；
- [ ] 安全充电并记录电量；
- [ ] 保存日志、bag、地图和参数；
- [ ] 更新 `docs/TEST_RECORD.md` 和 `docs/STATUS.md`；
- [ ] 提交小而明确的Git变更；
- [ ] 标注“已仿真”“已真机”“待验证”，禁止混写；
- [ ] 把下一次唯一首要问题写清楚。

## 21. 总体完成定义

以下条件全部满足，才算实物小车正式接管完成：

- 硬件型号、接线、系统和ROS环境有记录；
- 原始车载工作区和关键配置已备份；
- 底盘、编码器、IMU、雷达、相机、TF分别通过真机验证；
- 真机地图和Nav2连续3次通过；
- 寻物结果连续3帧一致，能报告物品和房间；
- 异常时能够停车并人工接管；
- 比赛入口在RDK X5上独立运行；
- MacBook/Windows断开不影响任务；
- 代码、地图、参数、日志和测试记录一一对应；
- 有明确的现场启动、停止和回退流程。
